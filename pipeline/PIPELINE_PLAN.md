# План работы по pipeline на неделю

## Зачем нужен этот pipeline

Цель этой недели — не строить «полноценный умный RAG-продукт», а **довести проект до аккуратного и воспроизводимого retrieval-эксперимента** на отчетах российских компаний.

Итог недели должен быть таким:

- есть **замороженная база чанков**;
- есть **исправленный gold set**, где каждому вопросу соответствует **один релевантный chunk_id**;
- есть **BM25 baseline**;
- есть **dense baseline на эмбеддингах**;
- есть **evaluation** с понятными retrieval-метриками;
- есть результаты, которые уже можно вставлять в отчет.

---

## Что уже лежит в папке `pipeline`

В папке лежат 5 ноутбуков:

1. `01_build_chunks.ipynb`
2. `02_fix_gold.ipynb`
3. `03_bm25_baseline.ipynb`
4. `04_dense_baseline.ipynb`
5. `05_evaluation.ipynb`

Они задают **основную логику всей работы**. Их нужно не переписывать заново, а **аккуратно довести до рабочего состояния**, реализовав недостающие части и соблюдая форматы файлов.

---

## Общая логика работы

Вся работа строится в таком порядке:

### Шаг 1. Собрать чанки
Сначала нужно получить **единый итоговый файл чанков**.

### Шаг 2. Зафиксировать gold set
Потом нужно привязать вопросы не к страницам, а к **конкретным чанкам**.

### Шаг 3. Построить retrieval baselines
После этого можно независимо запускать:
- BM25
- dense retrieval на эмбеддингах

### Шаг 4. Провести оценку
Когда готовы оба ranking-файла, считается evaluation.

---

## Что обязательно делать последовательно

Следующие этапы идут **строго по порядку**:

### Сначала обязательно:
1. `01_build_chunks.ipynb`

Без этого дальше двигаться нельзя, потому что:

После того как готовы:

- `gold_final.csv`

можно **параллельно** делать:
- `03_bm25_baseline.ipynb`

Ноутбук `05_evaluation.ipynb` запускается только после того, как готовы оба файла:
- `bm25_rankings.csv`
- `dense_rankings.csv`

---

## Приоритеты на эту неделю

### Обязательный минимум
Нужно обязательно получить:

- `chunks_final.csv`
- `gold_final.csv`
- `bm25_rankings.csv`
- `dense_rankings.csv`
- `per_query_results.csv`

Если эти файлы готовы и корректны, значит pipeline выполнен.

### Что не является обязательным на этой неделе
Сейчас **не нужно** тратить время на:

- генерацию ответов LLM;

- агентные пайплайны;
- сложную оптимизацию.

Сначала нужен **чистый retrieval-бейзлайн**, который можно защитить и объяснить.

# План по ноутбукам

## 1. `01_build_chunks.ipynb`

### Что делает
Из `DATA.zip` собирает финальный файл `chunks_final.csv`.

### Что важно
Это **базовый технический слой всего проекта**.
После согласования `chunks_final.csv` его **нельзя бесконечно пересобирать и менять**, иначе потом поедут gold set и все ranking-результаты. Создаём, кладём в репозиторий и больше не трогаем.

### Что нужно получить на выходе
Файл:
- `chunks_final.csv`

### Минимальные требования
В файле должны быть стабильные поля:
- `chunk_id`
- `company_raw`
- `company_slug`
- `source_file`
- `pdf_page`
- `chunk_idx_on_page`
- `text`
- `n_chars`

### Контрольная точка
Ноутбук считается готовым, если:
- файл `chunks_final.csv` успешно собран;
- `chunk_id` уникальны;
- пустых чанков нет;
- при повторном прогоне на тех же данных id не меняются;
- текст чанков читаемый и не выглядит сломанным.

### Что адаптируем из старой логики
Здесь по смыслу адаптируется уже существующая логика из старых файлов чтения PDF и чанкинга, но:
- делаем её аккуратной;
- делаем стабильные `chunk_id`;
- сохраняем результат в один итоговый csv.

---

## 2. `02_fix_gold.ipynb`

### Что делает
Берет исходный `goldenset.xlsx`, поднимает чанки нужной компании и страницы, выносит кандидатов в отдельный файл разметки, а затем собирает `gold_final.csv`.

### Что важно
Старый gold set был привязан к странице, а не к конкретному чанку.
Наша задача — **перейти от page-level разметки к chunk-level разметке**.

### Что нужно получить на выходе
Файлы:
- `gold_markup.xlsx`
- `gold_final.csv`

### Принцип разметки
Для каждого вопроса нужно:
- посмотреть все чанки нужной страницы;
- выбрать **один** релевантный чанк;
- записать его в итоговый gold.

### Контрольная точка
Ноутбук считается готовым, если:
- `gold_markup.xlsx` успешно собран;
- ручная разметка выполнена;
- `gold_final.csv` содержит по одной строке на вопрос;
- у каждого вопроса есть один `relevant_chunk_id`.

### Что адаптируем из старой логики
Здесь адаптируется старая идея сопоставления gold set со страницами, но **меняется ключевой уровень привязки**:
- раньше: вопрос → страница → все чанки страницы;
- теперь: вопрос → страница → ручной выбор → один chunk_id.

Это одно из самых важных исправлений во всем проекте.

---

## 3. `03_bm25_baseline.ipynb`

### Что делает
Показывает toy example для BM25, затем применяет BM25 к реальным данным и сохраняет ranking-файл.

### Что нужно получить на выходе
Файл:
- `bm25_rankings.csv`

### Формат результата
Колонки строго такие:
- `query_id`
- `method`
- `rank`
- `chunk_id`
- `score`

Где:
- `method = "bm25"`
- `rank` идет от 1 до `TOP_K`

### Контрольная точка
Ноутбук считается готовым, если:
- toy example полностью понятен и воспроизводится;
- на реальных данных построен ranking для всех вопросов;
- для каждого `query_id` есть top-k результатов;
- файл `bm25_rankings.csv` сохраняется в правильном формате.

### Что адаптируем
Здесь нужно **перенести логику toy example на реальные данные**:
- вместо игрушечного списка документов используем `chunks_final.csv`;
- вместо toy query используем `question` из `gold_final.csv`;
- вместо ручного просмотра результатов сохраняем итоговый ranking-файл.

---

## 4. `04_dense_baseline.ipynb`

### Что делает
Показывает toy example для dense retrieval, затем применяет embedding-модель `intfloat/multilingual-e5-large` к реальным данным.

### Что нужно получить на выходе
Файлы:
- `chunks_with_e5_embeddings.csv`
- `dense_rankings.csv`

### Формат `dense_rankings.csv`
Колонки строго такие:
- `query_id`
- `method`
- `rank`
- `chunk_id`
- `score`

Где:
- `method = "dense"`
- `rank` идет от 1 до `TOP_K`

### Что важно
Для модели E5 обязательно использовать префиксы:
- `query: ` для вопросов
- `passage: ` для чанков

### Контрольная точка
Ноутбук считается готовым, если:
- toy example работает и понятен;
- чанки закодированы в эмбеддинги;
- сохранен `chunks_with_e5_embeddings.csv`;
- для всех вопросов построен `dense_rankings.csv`.

### Что адаптируем
Здесь, как и в BM25-ноутбуке, нужно **перенести toy-логику на реальные данные**:
- сначала понять механику на маленьком примере;
- потом применить ту же идею к `chunks_final.csv` и `gold_final.csv`.

---

## 5. `05_evaluation.ipynb`

### Что делает
Показывает toy example оценки retrieval, затем считает метрики для:
- BM25
- dense retrieval
- random baseline

### Что нужно получить на выходе
Файлы:
- `per_query_results.csv`
- `metrics_summary.csv`

### Какие метрики считаем
Считаем 4 метрики:
- `Hit@10`
- `Recall@10`
- `MRR`
- `Mean First Relevant Rank`

### Что важно
В текущей постановке на каждый вопрос есть **один** релевантный чанк.
Поэтому:
- `Recall@10` должен совпадать с `Hit@10`

### Контрольная точка
Ноутбук считается готовым, если:
- собран `random` baseline;
- корректно построен `per_query_results.csv`;
- по всем методам посчитаны метрики;
- сохранен `metrics_summary.csv`.

### Что адаптируем
Сначала нужно понять идею оценки retrieval на toy example,
а затем перенести ее на реальные ranking-файлы:
- `bm25_rankings.csv`
- `dense_rankings.csv`
- `random_rankings.csv`

# Что важно не сломать

## 1. Не менять форматы файлов без необходимости
Если один ноутбук сохраняет файл в одном формате, следующий должен читать именно этот формат.

## 2. Не менять бесконечно `chunks_final.csv`
Сначала его нужно согласовать, а потом считать фиксированным.

## 3. Не менять `gold_final.csv` после запуска retrieval
Если gold set меняется после BM25/dense, результаты становятся несопоставимыми.

## 4. Не усложнять задачу раньше времени
Если базовый pipeline еще не доведен до конца, не надо параллельно строить интерфейсы, LLM-демо и гибридные схемы.

## 5. Проверять toy example перед реальными данными
Toy example нужен не «для красоты», а чтобы понять логику ноутбука до работы с реальными файлами.

# Что можно делать только после этого

После завершения основного pipeline можно думать о следующих шагах.

## Вариант 1. Hybrid + reranker
Можно попробовать:
- объединить BM25 и dense retrieval;
- затем добавить реранкер.

## Вариант 2. LLM + demo interface
Можно добавить:
- retrieval + LLM;
- простой демо-интерфейс.

## Вариант 3. LLM + сравнение с текущими baseline
Можно построить генеративный вариант и сравнить его с уже полученными retrieval-baselines.

Но все это:
- либо делается **только после завершения основной части**;
- либо просто записывается в раздел **future work / дальнейшие планы** в отчете.

На эту неделю основной приоритет — **закончить и стабилизировать retrieval pipeline**.
